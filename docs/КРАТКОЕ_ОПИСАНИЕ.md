# СтройРадар — краткое описание решения

Автоматизированный сервис поиска нарушений на строительных площадках Москвы.
Документ соответствует пункту 7.1 ТЗ.

## Подход и ключевые технологии

Система сопоставляет два независимых потока: снимки с камер видеонаблюдения и
календарный план СМР. На снимках распознаётся строительная техника, найденное
сводится к суткам и сравнивается с плановым этапом по методике «этап работ →
необходимая техника». На выходе — не рамки на фотографии, а ответ на вопрос
заказчика: идут ли работы так, как запланировано, и если нет, то почему.

Стек: Python 3.11, Ultralytics YOLOv8m, FastAPI, React 18 с Vite и Leaflet,
JSON-хранилище для прототипа. Запуск одной командой `docker compose up --build`,
GPU не требуется. Архитектура разделена на четыре слоя: `frontend`, `backend`
(API и приём файлов), `backend/domain` (методика, отклонения, статусы) и `ml`
(инференс). Домен не зависит ни от HTTP, ни от модели — он принимает словарь
«класс техники → количество», поэтому логика сопоставления покрыта тестами без
GPU и без загрузки весов.

## Процесс обнаружения техники

Модель дообучена из предобученных весов YOLOv8m на объединённом датасете
строительной техники: девять базовых классов плюс расширение из открытого набора
Roboflow (`roller`, `truck`, `crane_manipulator`, усиление `tower_crane`). Итого
12 классов — перечень ТЗ покрыт полностью. Обучение: 100 эпох, разрешение 640,
batch 16. Качество на валидации: Precision 0.821, Recall 0.832, mAP@50 0.859,
mAP@50-95 0.651.

Кадр обрабатывается в три шага: один прогон детектора с заведомо низким порогом
0,05, чтобы не потерять слабые объекты; фильтр с индивидуальным порогом
уверенности для каждого класса; сохранение результата вместе с путём к весам.
Пороги разные не случайно: башенный кран и грузовик модель распознаёт хуже — им
мягче, бетономешалку легко спутать с обычным грузовиком — её отсекаем строже.

Скорость на CPU: медиана 0,52 с на кадр, около 1,9 кадра в секунду. Замеры видны
в рантайме — `/api/detect` возвращает `inference_ms`, `/api/demo/analyze` —
среднее и максимум по пачке кадров.

## Схема сопоставления с этапами строительства

Единица сопоставления — **сутки**, а не отдельный кадр: снимок показывает
мгновение, а плановый этап длится неделями. Методика опирается на две сущности.
**Маркер** — машина, по которой этап опознаётся однозначно. **Звено** — набор
машин, без которых работа физически не идёт: внутри группы достаточно любой
машины, но все группы должны быть закрыты одновременно.

| Этап СМР | Маркеры | Звено |
|---|---|---|
| Расчистка участка | бульдозер, погрузчик | самосвал или грузовик |
| Откопка котлована | экскаватор | самосвал или грузовик |
| Устройство фундаментов | сваебой | автокран или кран-манипулятор |
| Монтаж каркаса, стены и перекрытия | башенный кран, бетономешалка, бетононасос | бетономешалка и бетононасос, если бетон уже есть |
| Благоустройство | каток | не требуется |

Дата съёмки определяет плановый этап из графика; детекции за эти сутки
агрегируются в количество машин по классам; проверяется наличие маркера и полнота
звена. Звено каркаса проверяется только при появлении бетономешалки или
бетононасоса: башенный кран без бетона этап закрывает сам. Если на кадрах машины
разных этапов, берётся более узкий сигнал: фундаменты, благоустройство, каркас,
котлован, расчистка. Самосвал, грузовик, автокран и кран-манипулятор этап сами
не открывают. Результат — до трёх типов отклонений: `missing_required` (этап идёт,
маркерной техники нет), `incomplete_link` (маркер есть, звено разорвано),
`unexpected_equipment` (техника другого этапа). Каждое отклонение несёт
формулировку, зону из плана и ссылки на снимки-подтверждения, поэтому
предупреждение можно проверить, а не только прочитать. Статус дня выводится из
набора отклонений, объект получает худший статус среди дней со съёмкой: простой,
возможное нарушение, опережение графика, норма, нет данных.

Пример из ТЗ воспроизводится напрямую: на этапе откопки котлована экскаватор
виден, самосвалов нет — система предупреждает о возможном снижении темпа работ с
указанием зоны и снимков. Сценарий закреплён автотестом
`test_incomplete_link_like_tz_example`.

## Текущий прогресс

Все обязательные функции раздела 2 ТЗ реализованы и работают на реальных снимках:
детекция 12 классов; сопоставление с графиком по 5 этапам, планы в CSV и Excel
с русскими названиями этапов; визуализация — дашборд города с картой и кадрами с
камер, карточка объекта с таймлайном план/факт, просмотр снимка с рамками,
страница с описанием методики; три типа отклонений с зоной и
снимками-подтверждениями.

Демо-сценарий запускается двумя нажатиями: «Загрузить демо-данные» подставляет
план и 15 кадров из папки `Демо`, «Запустить анализ» выдаёт таймлайн. День
открывается кнопкой «Открыть»: в окне статус, предупреждение, зона и кадр.
Воспроизводимость обеспечена Docker Compose, скриптом загрузки весов и тестами
методики. Проверочный набор собран скриптом `eval_model`: просмотрено 86 кадров,
в набор отобрано 17, отчёт — `docs/отчёт_тестирования.md`.

## План работ до финальной сдачи

1. Приём кадров по RTSP и очередь задач — контроль в режиме, близком к реальному времени.
2. Перенос хранилища в PostgreSQL: изолирован в одном модуле, даёт историю по десяткам тысяч объектов.
3. Трекинг техники между кадрами — учёт машино-часов, а не только факта наличия машины.
4. Расширение методики на отделочные и инженерные работы: этапы задаются данными, не кодом.
5. Дообучение на данных заказчика по спорным кадрам из накопленной истории.
6. Публичный стенд: развёртывание контейнеров на внешнем хосте для проверки по ссылке.
